## 一、产品定义

**一个能听、能说、能自己操作电脑的独立桌面软件。** 不是 DSH 的外挂，自带大脑（agent loop），只从 `dsh-computer-use`（MIT）复用了 computer-use 能力。

三条硬性体验指标：

| 指标 | 目标 | 现状 |
|---|---|---|
| 唤醒到响应 | < 500 ms 感知 | 待实现 |
| 语音到语音 | 1.2–1.6 s | 链路各段已实测 |
| 打扰度 | 不占麦、不抢焦点、可随时关 | 麦克风共享已实测通过 |

## 二、新增需求（R5–R7）与它们的连带影响

### 2.1 R5 语音唤醒可关闭

- 关闭后**释放采集流**，不是"停止识别但仍占麦"。托盘麦克风指示必须消失。
- 降级为全局热键（按住说话）或纯文字输入。
- 关闭唤醒 ≠ 关闭语音输入：热键说话仍然可用。两者解耦。

### 2.2 R6 TTS 可关闭 —— 有个隐性代价必须说清

关闭 TTS 后，**高风险操作无法再用语音确认**（没法提问，也就没法回答）。

所以在 v0.4 里，确认通道随 TTS 状态自动切换：

| TTS | 高风险确认方式 |
|---|---|
| 开 | 语音确认（完整短语 + 防自触发闸门） |
| **关** | **HUD 卡片物理确认（点击/回车）** |

这一点必须在设置页明示："关闭语音后，危险操作需要手动点击确认"。否则用户会以为助手坏了。

**建议拆成两个开关**（待确认）：
- `语音播报`：助手是否出声
- `语音确认`：高风险时是否用语音提问
只关播报、保留确认提问，是可能的（只在那一次提问时出声），体验更好。

> ✅ **已定（2026-10-27）：拆成两个独立开关。**
> `语音播报` 关闭时全程静默；`语音确认` 独立控制高风险提问是否出声。
> 两者组合的确认通道见 §7 矩阵：只要 `语音确认` 关闭，一律走 HUD 物理确认。

### 2.3 R7 权限可设置

见 §6，是本次新增的最大一块设计。

## 四、架构

```
┌──────────────────── 独立桌面应用（Electron 44）────────────────────┐
│  渲染层：悬浮 HUD / 字幕 / 审批卡片 / 设置页                        │
│  主进程                                                             │
│   ├─ AudioService   共享模式采集(16k) + AGC + 释放控制              │
│   ├─ WakeService    常驻 KWS（可关闭，关闭即停流）                   │
│   ├─ AsrService     sherpa-onnx 流式                                │
│   ├─ TtsService     sherpa-onnx bronya + 动态压缩（可关闭）          │
│   ├─ PermissionGate ★ 权限决策 + 审计日志                           │
│   ├─ Orchestrator   状态机 / 打断 / 播报策略 / 确认通道             │
│   ├─ AgentLoop      自研，LLM + tool calling（云端/本地可切）        │
│   └─ CuaToolkit     ← vendor 自 dsh-computer-use（MIT，零依赖）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ NDJSON（dsh-cua/1）
                    ┌──────────▼──────────┐
                    │ powershell 5.1 + cua.ps1 │
                    └─────────────────────┘
```

**新增 `PermissionGate`**：所有工具调用必须先过它，再做实际动作。这是 R7 的落点，也是后面审计日志的唯一入口。

## 五、语音链路

### 5.1 采集（已实测）

- WASAPI **共享模式**，永不申请独占。
- 16 kHz 单声道，20 ms 帧。
- **AGC 必做**：实测 -49.6 dBFS → 目标 -22 dBFS，带噪声门限。
- 设备策略：唤醒词固定绑**内置麦克风阵列**，不走蓝牙耳机（避免 A2DP→HFP 切换导致输出音质骤降）。

### 5.2 唤醒

- 常驻 KWS，目标 CPU < 2%。
- 可关闭；关闭即 `stream.stop()` 释放设备。
- 命中后：提示音 + HUD 亮起 + 进入 LISTENING。

### 5.3 TTS（定稿）

- 模型 `vits-zh-hf-bronya`（116 MB，22.05 kHz），CPU 推理。
- 重音压缩 beta=0.0、限幅 ±22 dB、平滑 45 ms，输出重采样至 44.1 kHz。
- 首包 ~100 ms，RTF 0.15。
- 可关闭（见 §2.2）。

## 六、权限系统（R7）

### 6.1 设计目标

不是"全有全无"，而是**按能力拆分 + 分级 + 可追溯**。

### 6.2 权限级别

| 级别 | 语义 | 行为 |
|---|---|---|
| `allow` | 允许 | 直接执行，HUD 轻提示 |
| `ask` | 每次询问 | 弹卡片，等待确认（语音或物理，见 §2.2） |
| `deny` | 拒绝 | 不执行，回填一条明确的拒绝说明给模型 |
| `allow_once` | 限时允许 | 本次会话/15 分钟内有效，到期自动回落 |

### 6.3 能力清单（默认值建议）

| 类别 | 能力 | 默认 |
|---|---|---|
| 感知 | 截图 | `allow` |
| 感知 | 读取窗口/UI 元素 | `allow` |
| 感知 | 读剪贴板 | `ask` |
| 感知 | 常驻麦克风（唤醒） | `allow`（可关） |
| 输入 | 鼠标移动/点击/滚动 | `allow` |
| 输入 | 键盘输入 | `allow` |
| 输入 | 剪贴板写入 | `ask` |
| 输入 | 启动/关闭应用 | `allow`（关闭=ask） |
| 数据 | 读文件（工作目录内） | `allow` |
| 数据 | 读文件（工作目录外） | `ask` |
| 数据 | 写/改文件 | `ask` |
| 数据 | **删除文件** | `ask` |
| 通讯 | 发送消息（邮件/IM） | `ask` |
| 通讯 | 支付/转账 | `deny`（默认关闭，需显式开启） |
| 系统 | 修改系统设置 | `ask` |
| 系统 | 关机/重启/安装软件 | `deny` |
| 模型 | 云端 LLM（对话内容外发） | `allow`（可切本地） |

> 默认策略的取向：**低风险默认放行以保证流畅，不可逆动作一律询问，破坏性系统操作默认拒绝。**

### 6.4 作用域（比"逐项开关"更重要）

单个开关不够用，真实场景要"限定范围"（**已定：三档作用域全部要做，按应用白名单在 P5 落地**）：

- **按应用**：只允许操作"浏览器 + 记事本 + 微信"，其他应用一律 ask
- **按目录**：只允许写 `D:\workspace` 下，其他 ask
- **按时间**：`允许 15 分钟` / `仅本次会话` / `永久`

### 6.5 审计日志

每次 `ask` 与高风险 `allow` 都记录：

```json
{"ts":"2026-10-27T20:15:03+08:00","capability":"file.delete","target":["D:\\a.txt"],
 "level":"ask","decision":"allow","channel":"voice","utterance":"确认删除这个文件",
 "result":"ok","duration_ms":412}
```

- 本地 JSONL，可导出
- 用户可在设置页按时间/能力筛选
- 这是"出事后能查"的底线

### 6.6 与系统权限的关系

我们**不试图绕过** Windows 的麦克风隐私开关，也不应该。系统权限是前提，应用内权限是细分。
两层都满足才能动作；任一层拒绝都要给出**可操作的指引**（"去 设置→隐私→麦克风 打开"）。

### 6.7 权限 UI

- **首次运行引导**：选档（保守 / 标准 / 宽松），再逐项微调
- **设置页**：能力矩阵表，一行一个能力，右侧下拉选级别 + 作用域
- **HUD 快捷**：`暂停 10 分钟`（全 deny，一键静音但继续监听）

## 七、交互模式矩阵（R5 × R6 的组合）

| 唤醒 | TTS | 形态 | 高风险确认 |
|---|---|---|---|
| 开 | 开 | 完整语音助手 | 语音（含防自触发闸门） |
| 开 | **关** | 只听不说，看字幕 | **HUD 物理确认** |
| **关** | 开 | 热键说话/文字输入，语音回复 | 语音 |
| **关** | **关** | 纯文字助手（零麦克风占用） | HUD 物理确认 |

第四种是最保守形态：**完全不碰麦克风**，适合会议中、公共场合。

## 十三、模型配置（R9）

### 13.1 数据层

- 配置文件：`.config/agent.json`（可用 `CUA_VA_CONFIG_DIR` 覆盖）
- 写入用 **临时文件 + rename**，避免写一半崩了留下坏配置
- 环境变量 `CUA_VA_API_KEY` 优先级高于文件（临时覆盖，不必落盘）

### 13.2 密钥语义（三个值含义不同）

| 传入 | 行为 |
|---|---|
| `"sk-xxx"` | 替换为新密钥 |
| `""`（空串） | **不修改**，保留原值 |
| `null` | **清除**密钥 |

界面上读取到的永远是掩码（`sk-d****\*\*\*\*3456`），且带 `hasApiKey` 布尔给 UI 判断。

> 踩过的坑：第一版只有"空串=不修改"，导致测试密钥无法通过界面清除，会残留并随请求发到真实端点。补了 `null=清除` 才闭环。

## 十六、首字延迟拆解与优化（2026-10-27）

### 16.1 基准：TTFT 到底是多少

5 轮交错采样（每轮打乱顺序，抵消服务端漂移），中位数：

| 用例 | payload | 连接 | 首字节 | **TTFT** | 总计 |
|---|---|---|---|---|---|
| A 最小请求（无 tools） | 0.1 KB | 134 | 145 | **901** | 920 |
| B 正式 system（无 tools） | 0.8 KB | 123 | 127 | **944** | 944 |
| C 正式 system + 12 工具 | 12.6 KB | 134 | 144 | **1333** | 1345 |
| D 单工具（action 枚举） | 1.2 KB | 134 | 142 | **1322** | 1332 |

**结论**：
1. **基线首字 ~0.9s**，与官方客户端体验一致——我们的设置没有问题。
2. **带 tools 时 +0.4s**，且**与 schema 体积无关**：12.6KB 与 1.2KB 的 TTFT 几乎相同（1333 vs 1322）。
   说明这是服务端 tool-calling 解码路径的开销，不是"我们发了太多 token"。
3. 网络（连接建立）只占 ~130ms，不是瓶颈。

### 16.2 真正的问题：模型不吭声就直接调工具

逐轮计时发现，一次任务的 3.2s 是这样构成的：

```
轮1 决定调工具    875ms  ← 无任何文本输出，用户听不到东西
工具执行          321ms
轮2 生成回答     1728ms  ← 首字在这里
生成             258ms
```

**用户要等 3.2s 才听到第一个字**，不是因为模型慢，而是因为第一轮"只出工具调用、不出文本"。

### 16.3 修复：强制先说一句再动手

system prompt 加一条硬规则：

> 每次调用工具之前，先说一句极短的话（不超过 15 字）告诉用户你要做什么。

**效果实测**（4 次）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 首个可播报文本 | 无（要等 3.2s） | **626 / 689 / 736 / 1125 ms**（中位 ~0.7s） |
| 轮1 输出 | 0 字符 | 11–15 字符（正好一句白描） |
| 端到端完成 | 3.2s | 2.1–6.1s（随步数变化） |

**首字 ~0.7s 已经优于 v0.4 定的 1.2–1.6s 目标**，而且这句话本身就实现了"动作白描"，一举两得。

### 16.4 仍需注意

- 多步任务端到端可达 6s（实测有一次跑了 4 轮 LLM），但**每轮之间都有白描播报**，感知上不是"卡住"。
- 工具结果文本会进入下一轮 prefill，实测轮2 TTFT 在 825–1728ms 之间波动，与工具输出长度相关。
  → 工具结果已限制 1200 字符，后续可再压到 800。

### 16.5 流式（已确认开启）
`packages/agent/loop.mjs` 对每次 LLM 调用显式传 `stream: true`，
`LLMClient` 据此走 SSE，逐块解析 `content` 与 `tool_calls` 增量。

这条不是可选项——**"首字 0.7s"和"先说话后动手"两个效果都依赖流式**：
非流式下必须等整段生成完才能拿到第一个字，首字会退回秒级。

`tools/verify-p1.mjs` 里断言了 `text_delta` 事件数量，流式一旦被关掉会立刻失败。

## 十九、P2-b · 自适应 AGC + VAD（2026-10-27，已通过）

### 19.1 设计前提：不能按"当前环境"把参数调死

用户原话：「**现在吵，之后不一定**」。所以这套东西必须满足：
安静房间能用、吵闹宿舍也能用，**不靠手工改阈值**。

| 组件 | 规则 |
|---|---|
| 噪声底估计 | 自动跟踪当前环境，不启动标定 |
| VAD | 阈值 = 噪声底 + 12 dB（相对值，不是绝对 dBFS） |
| AGC | 只放大被判为语音的帧；静音/噪声不放大 |

### 19.2 噪声底估计：走过两条弯路才定下来

| 方案 | 结果 |
|---|---|
| 纯最小值跟踪（无下限） | ❌ 一个数字静音帧就把底噪拉到 -180 dB，之后整段都判语音 |
| 滑动窗口分位数 | ❌ 语音占比高的素材里，分位数落进语音，底噪被抬高 → 什么都检不出 |
| **最小统计 + 下限 -70 dB + 分语音/非语音两档上升速度** | ✅ 安静与吵闹都成立 |

配合把起始阈值从 9 dB 提到 **12 dB**：噪声的正常波动（±10 dB）不至于触发。

### 19.3 实测（16 kHz，素材在 `assets/test/`）

| 用例 | 噪声底 | 判为语音比例 | 精确率 | 召回率 |
|---|---|---|---|---|
| **合成纯噪声（无人声）** | -43.0 | **0.000** | — | — |
| 宿舍实录（可能含人声） | -52.8 | 0.806 | — | — |
| 干净语音 | -70.0 | 0.759 | 1.000 | 1.000 |
| SNR 20 dB | -46.6 | 0.774 | 0.970 | 0.989 |
| SNR 10 dB | -37.3 | 0.781 | 0.945 | 0.972 |
| SNR 5 dB | -33.0 | 0.485 | 0.914 | 0.583 |
| SNR 0 dB | -30.1 | 0.134 | 0.855 | 0.151 |

> 宿舍实录实测底噪 **-42.2 dBFS**，比安静环境（-49.6）高约 7 dB。

### 19.4 一个必须说清的边界

**宿舍实录被 100% 判成语音，很可能是因为室友本来就在说话。**

这不是 VAD 的 bug——按能量分不开"我"和"室友"。要区分"谁在说"得靠：
- **唤醒词（KWS）**：只对特定短语响应
- **声纹校验**：确认是不是本人

所以验收口径改成：**"空场不误触发"用合成纯噪声验证**（0 触发 ✅），
宿舍实录单独记录、不当作失败。不说清这点，后面容易误判成"VAD 没用"。

### 19.5 AGC 实测

| 用例 | 语音帧中位增益 |
|---|---|
| 干净语音（输入 -18.9 dBFS） | **-1.9 dB**（不硬拉） |
| SNR 10 dB 混合 | -1.6 dB |
| 宿舍实录 | +23.9 dB（被判成语音才放大） |

安静时不硬拉增益，正是"自适应"要达到的效果：若按宿舍标准固定 +20 dB，
安静环境会把底噪直接放大成嘶声。

### 19.6 交付物

| 文件 | 说明 |
|---|---|
| `packages/voice/agc.mjs` | 噪声底跟踪 + 自适应 AGC（攻击 10ms / 释放 200ms） |
| `packages/voice/vad.mjs` | 自适应能量 VAD（迟滞 + 最短语音 + 拖尾 300ms） |
| `tools/verify-vad.mjs` | 六种用例的验收脚本 |
| `tools/make-test-audio.py` | 录底噪、按 SNR 混合素材 |

## 二十一、P2-d · 采集接入 Electron + 流式管线（2026-10-27，已通过）

### 21.1 架构

```
隐藏渲染进程（capture.html）
  getUserMedia(16k, 单声道)
  → AudioWorklet 攒成 1600 帧（100ms）
  → IPC 送 Float32Array 给主进程
主进程
  → StreamingPipeline：噪声底/AGC → VAD 迟滞 → KWS
  → 命中唤醒词 → showForWake（不抢焦点）
```

为什么放渲染进程：**Electron 主进程没有麦克风 API**，`getUserMedia`/`AudioContext` 只在渲染进程可用。
用 AudioWorklet 而不是 `ScriptProcessor`：后者跑在主线程，界面一卡就掉音频。

### 21.2 采集实测

| 检查项 | 结果 |
|---|---|
| 采集启动 | ✅ 16000 Hz，设备 `Default - 麦克风阵列 (Realtek)` |
| 数据流 | ✅ 稳定 10 块/秒（每块 100ms） |
| 电平 | 底噪环境约 -36 ~ -48 dBFS |
| 关闭释放 | ✅ `listening=false`、采集窗口已销毁 |
| **判定** | **`pass: true`** |

### 21.3 流式管线验收（离线，确定性强）

实机"扬声器放唤醒词 → 麦克风收"受音量、AEC、房间影响，不能作为管线正确性判据
（本次就撞到了：系统静音导致测不通）。改用固定音频直接喂管线：

| 用例 | 峰值 | AGC 中位增益 | 唤醒 |
|---|---|---|---|
| 正常唤醒词 | -13.8 dB | **0.0 dB**（已够响，不加热） | ✅ 你好小助手 |
| 非唤醒词句 | -10.4 dB | 0.9 dB | ✅ 未触发 |
| **弱信号（衰减 24dB）** | **-37.8 dB** | **+20.6 dB** | ✅ 仍然命中 |

## 二十二、主题外观与闪烁修复（2026-10-27）

### 22.1 闪烁的三个来源，逐个堵

| # | 来源 | 处理 |
|---|---|---|
| 1 | **可见状态下 resize**（原来每次内容变高都 `hide → setSize → show`） | 窗口高度**固定 300**，卡片在渲染层贴底自适应，全程不 resize |
| 2 | **首帧未绘制就 show** | 等 `ready-to-show` 事件 + 渲染层就绪信号，两者都到才显示 |
| 3 | 布局在隐藏窗口里量不准 | 用 `setTimeout` 上报就绪（`requestAnimationFrame` 在隐藏窗口不触发） |

而用 hide/show 绕开残影就会闪一下。固定高度后两个问题一起消失。

> 代价：对话期间窗口占 380×300，卡片下方留白（透明）。
> 因为只在被唤醒时存在，不影响平时使用；换取了"零 resize、零闪烁"。

| 头部头像 | `avatar.jpg` 40×40 圆角，角色居中裁切 |
| 强调色 | 取自插画：聆听紫 `#8a5cf6`、播报青 `#22b8cf`、确认按钮 `#6d3fd1` |

## 二十三、P3-a · ASR 接入与"说 → 做 → 说"闭环（2026-10-28，已通过）

### 23.1 为什么这一步是分水岭

前面所有环节都是"哑的"：KWS 能判断是不是在叫我，VAD 能判断有没有人说话，
但谁也不知道我说了什么。ASR 接上之后，"唤醒 → 说 → 它真的动手 → 它回话"才成立。

### 23.2 选型：为什么是这个模型

| 候选 | 体积 | 取舍 |
|---|---|---|
| `streaming-zipformer-zh-2025-06-30` | 566MB | 太大，冷启动更慢 |
| **`x-asr-480ms-zh-en-punct-int8-2026-06-05`** | **128MB** | **带标点、中英混说、480ms 分块，选它** |
| `small-ctc-zh-int8-2025-04-01` | 20MB | 太小，识别质量掉档，留作低配后备 |

选它的三个理由：**带标点**（字幕可读性完全不是一个档次）、**中英混说**（"打开 VS Code"这种指令很常见）、
**int8**（CPU 上 RTF 0.08，实时性有 12 倍余量）。

下载走 `gh-proxy.com` 镜像（直连 GitHub 实测只有 6KB/s，镜像 965KB/s，128MB 用了 230 秒）。
注意：这台机器上 7897 端口的代理当时已经关了，直连 GitHub API 可用但下载被限速。

### 23.3 实测数据（本机 16GB / 144DPI）

| 指标 | 数值 | 说明 |
|---|---|---|
| 模型加载 | 6.2–6.7s | **冷启动，只能付一次**；同步原生调用，会独占主线程 |
| 常驻内存 | +241MB（38 → 279MB） | int8 编码器 148MB + ORT 工作区，推理后再涨 13MB |
| 首字（说话到出字） | 130–153ms | 相对于"第一块音频进入" |
| 首字（相对语音起点） | ~800ms | 480ms 分块模型的固有延迟 |
| RTF | 0.075–0.082 | 12 倍余量 |
| 端点判定 | 尾静音 2.4s / 标点后 1.2s / 单句上限 15s | 给"我还没说完"留犹豫时间 |

识别质量（TTS 合成音回环，22.05k → 重采样 16k）：
`帮我把浏览器打开，然后搜索今天的天气` → 一字不差，标点也对。

### 23.4 三个必须记住的坑

**坑一：模型加载独占主线程。** `new Asr()` 是同步原生调用，6.5 秒内主进程什么都干不了。
实测有一次预热和一次工具调用撞在一起，`list_windows` 从 467ms 拖到 9771ms。
处理：预热前检查 `activeTurn`/`commandActive`，在对话中就推迟 20 秒再试。

**坑二：Electron 不允许 native 外部缓冲区。** TTS 在系统 Node 下正常，在 Electron 里必然报
`External buffers are not allowed`（同步路径）或 `TTS settlement failed`（异步路径）。
根因是 `sherpa-onnx-node` 默认把音频以外部 ArrayBuffer 交回 JS。
修法：`generateAsync({ ..., enableExternalBuffer: false })`，让原生侧拷贝一份。
**这条只影响 TTS**，ASR/KWS 返回的是字符串和布尔值，不受影响。

**坑三：唤醒词会污染指令。** 唤醒命中的那一刻，"你好狼宝"四个字已经进了麦克风。
所以唤醒后 300ms 内的音频丢弃，识别从 300ms 之后才开始，否则指令会变成"你好狼宝打开浏览器"。

### 23.5 字幕与播报的分工

```
麦克风 100ms/块
  ├─ pipeline.push()      → 电平 / 语音标记 / 唤醒命中（常开）
  └─ feedCommandAudio()   → 仅唤醒后 15s 窗口内
        ├─ partial 非空 → 推字幕（文字没变就不推，避免 10 次/秒重绘）
        └─ final（端点）→ finishCommand → runCommand
```

播报不按整段合成，而是**按句切、逐句合成播**：一句 60 字的回答要 2.6 秒才出第一段音频，
切到 22 字以内后每句 300–600ms 就能开口。实测一轮 173 字的回答被切成 8 段，
最后一段播完时距用户说完约 7.5 秒。

半双工硬闸：`selfSpeaking()` 期间忽略唤醒命中（含播完后 600ms），
否则助手会被自己的声音唤醒。真全双工要等 AEC。

- **打断**：播报中用户开口不会停（需要 VAD + 播报门控联动）。

## 二十四、P3-b · 打断（barge-in）（2026-10-28，已通过）

### 24.1 为什么打断不是"锦上添花"

助手一旦开口就是 5~10 秒。这期间用户想改口（"不对，我是说右边那个"）、想喊停（"等一下"），
如果不打断，就只能等它念完再说一遍。所有做得好的语音助手都支持打断，不是因为高级，是因为没它没法用。

### 24.2 先量回声，再定阈值

打断能不能做成，取决于"我说话时麦克风听到多少自己的声音"。
本机实测（`--echo-test`，连续播报 19.8 秒，AEC 开启）：

| 指标 | 静默期 | 播报期 | 差值 |
|---|---|---|---|
| 中位电平 | -56.0 dB | -55.7 dB | **+0.3 dB** |
| P90 | -55.5 dB | -54.4 dB | +1.1 dB |
| 最大值 | -55.0 dB | -43.7 dB | **+12.3 dB** |
| 被判成"有语音"的比例 | 0% | **0%** | — |

结论：Chromium 的 AEC 把我自己的声音压到了底噪附近，连峰值也只有 +12.3dB。
所以**不需要自研回声消除**——只要把门限定在 13dB、并要求持续 300ms，就能把回声和人声分开。

### 24.3 判定器（`packages/voice/bargein.mjs`）

| 参数 | 值 | 理由 |
|---|---|---|
| `marginDb` | 13 | 压住实测回声峰值（12.3dB）；再低会把扬声器残留当人声 |
| `holdMs` | 300 | 单个爆音/咳嗽不该打断 |
| `settleMs` | 250 | 播报起头时扬声器有瞬态 |

纯逻辑验收 8 个用例全部通过（`node tools/verify-bargein.mjs`）：
纯回声 20 秒不误触发、22dB 人声 300ms 内触发、100ms 爆音不触发、门限边缘 14dB 触发、
12dB 持续 2 秒不触发（这是回声与人的分界线）、断续短促不触发、reset 后可再次触发。

### 24.4 打断发生后必须同时做对三件事

1. **立刻停声**：`stopSpeaking()` 清空队列并向渲染层发 `hud:stopAudio`。
   只停当前这一句是不够的——队列里还有七八句，下一句会紧接着念出来。
2. **直接进聆听**：不再要求说唤醒词（用户已经在说话了）。
3. **回灌最近 600ms 音频**：用户开口说的是"等一下"，如果从"下"字开始记，
   就会识别成"等一"甚至听不清。所以采集链路一直保留最近 600ms 的块，打断时先喂给识别。

实测（注入 25dB 人声、真实播放下打断）：
`{"detected":true,"latencyMs":277,"audioStopped":true,"queueEmpty":true,"stateAfter":"listening","asrArmed":true}`

### 24.5 这一步暴露的三个坑

**坑一：播报其实一直没出声。** HUD 的 CSP 是 `default-src 'none'` 且没写 `media-src`，
`new Audio('file:///...')` 被静默拦掉——`<audio>` 触发 `error`，我的代码把它当成"播完了"，
于是日志里一片 `spoken N ok`，实际一点声音都没有。
**看日志看不出来，必须看渲染层 console**。修法：`media-src 'self' file: blob:`。
这条也解释了为什么此前"播报很快结束"：全部是错误路径。

**坑二：`maxNumSentences: 1` 会静默截断。** sherpa-onnx TTS 默认只合成第一句，
传给它的多句文本会被直接丢掉——字幕显示三句、只读第一句。改成 8 并写进 DEFAULTS。

**坑三：ASR 预热把打断冻住。** 模型初始化是同步原生调用，独占主线程 6 秒；
这 6 秒里采集块进不来，打断检测完全停摆（实测 `detector.elapsedMs=0`）。
预热条件因此扩展为：`activeTurn || commandActive || playingAudio() || 队列非空` 就推迟。

### 24.6 验收命令

```bash
node tools/verify-bargein.mjs                    # 判定逻辑（8 例）
node tools/run-shell.mjs --echo-test             # 回声实测（需要能出声的扬声器）
node tools/run-shell.mjs --bargein-test inject   # 链路：检测→停声→进聆听→接识别
```

### 24.7 局限（必须说清楚）

本机 Windows 的 AEC 是**系统级**的，参考信号是整个系统输出。
所以"用另一个进程播放一段人声"仍会被消掉——靠扬声器回放**模拟不了真人说话**。
`--bargein-test <wav>` 的声学分支只能观察回声行为，真正的人声验证要用户本人开口。
`inject` 分支验的是链路，判定逻辑由单测覆盖，两者合起来才算验证完整。

## 二十五、P3-c · 权限门（R7）（2026-10-28，已通过）

### 25.1 定位

`PermissionGate` 是**唯一**能说"能不能做"的地方，也是审计日志的唯一入口。
散落在各个工具里的 break-glass 检查一定会有漏网的——权限这件事只能有一个收口。

它不碰 UI、不碰音频：`confirm` 作为回调从外部注入。这样权限引擎能在纯 Node 里单测，
也方便以后换确认通道（语音 / 点击 / 手机 / 硬件键）而不动策略代码。

### 25.2 级别与能力

| 级别 | 行为 |
|---|---|
| `allow` | 直接执行，不打扰 |
| `ask` | 弹确认卡片（语音或点击），12 秒不回应按拒绝 |
| `deny` | 不执行，把原因回填给模型 |
| `allow_once` | 15 分钟内同样的操作不再问 |

能力默认值（标准档）：感知与指针/键盘/启动 = `allow`；剪贴板读写、改文件、删除、发消息、系统设置 = `ask`；
关机/重启/安装、支付转账 = `deny`。三档预设（保守/标准/宽松）只改默认级别，用户覆盖优先。

### 25.3 机械风险靠策略，语义风险靠模型

工具参数里能看出风险的只有两类，所以按"具体值"升级而不是整类抬高：

| 触发 | 升级到 | 理由 |
|---|---|---|
| `Win+R` / `Win+X` / `Win+I` / `Win+L` / `Ctrl+Shift+Esc` / `Alt+F4` | `ask` | 单按一个键无害，这些组合等于"能执行任意命令/关掉正在改的文档" |
| 输入文本里出现 `rm -rf` / `del /s` / `format c:` / `shutdown` / `git push -f` | `ask` | 模型把这句话打进终端或运行框就真会执行 |

"这个按钮点了会不会付款"这类语义风险，机械层看不出来——归模型的自觉（系统提示第 6 条）与用户确认。

### 25.4 确认通道

HUD 弹卡片，同时开一个短识别窗口：说「确认」或「取消」都行，点按钮也行，12 秒不吭声按拒绝。

`parseConfirmText` 的关键在**否定词先判**：中文的"不用了""不要"里也含"用/要"，
先匹配肯定词会把拒绝读成同意——这类错误在删除确认上代价最大。
单测覆盖 7 种说法（确认 / 可以执行吧 / 不用了 / 不要确认这个东西 / 取消 / 嗯… / 空串）。

### 25.5 被拒绝之后：模型会想办法绕

实测踩到两次，都是真实行为，不是假想：

1. **重试循环**：模型把"等太久没有回应"理解成"超时了，再试一次"，于是卡片反复弹。
   处理：拒绝理由里明确写"这次不做，不要重复尝试"；同一回合同一工具被拒两次就不再问。
2. **迂回绕过**：读剪贴板被拒之后，模型自己去**打开记事本粘出来看**（`open_application notepad`）。
   处理：系统提示加第 7 条——被拒就停，不要用别的路径达到同样目的，直接告诉用户没做成。

### 24.8 改版：打断改为唤醒词触发（2026-10-28 下午）

用户反馈：「打断也做一下唤醒词吧，就用等一下当唤醒词，要不然有点声就被打断了」。
原设计（能量法）在宿舍这种开放环境里确实不成立——咳嗽、笑、室友说话都会让它闭嘴。

**为什么不用 KWS 找「等一下」**：项目里已有的 KWS 模型（wenetspeech 3.3M）对
训练集外的短词能力很弱。实测把「等一下」的 8 种音素写法（`d ěng y ī x ià`、
`y í`、`y i`、`iǎ` 变体…）× 12 组阈值（score 1.0/1.5/2.0/3.0 × threshold 0.25/0.15/0.1）
全部 **0 命中**；而同一个 ASR 模型对同一段音频给出的就是「等一下」，一字不差。
所以改用 **ASR 文本匹配**：延迟高一点（约 1.1s），但真的能听见。

模型自带的示例关键词（`x iǎo ài t óng x ué @小爱同学` 等 8 个）没有这个问题——
它们的音素切分是"声母 + 带调韵母"（`iǎo`/`uó`），我最初把 `xià` 拆成 `i`+`à`，
格式本身就错了；但即使按正确格式（`x ià`）重测仍然 0 命中，结论不变。

**实现**：`AsrSession` 提供"共享同一个模型、各自独立解码状态"的多条流
（`Asr.newSession()`）。播报开始时开一条专用于打断的流，逐句重建，避免上一句的假设带过来。

**两条闸门同时满足才打断**：
1. 识别文本里出现约定词（等一下 / 等一等 / 等会儿 / 停一下 / 别说了 / 先停下）
2. 电平确实高于底噪（防止识别器对静音产生幻觉）

**一个必须用峰值的坑**：关键词通常落在句尾，等识别把字吐出来时，当前这一块往往已经静音，
用"当前块电平"判定会得到 `too quiet` 而白白丢掉正确的文本（实测连续四次）。
改成"最近一秒的最高电平"（每块衰减 8%）才稳定。

**实测**（`--bargein-test kw|negative`，把 WAV 按 100ms 块喂进真实链路）：

| 场景 | 结果 |
|---|---|
| 播报中喂「等一下」 | 1.12s 后打断，停声 → 进聆听 → 接识别，全部生效 |
| 播报中喂「今天天气不错，我们出去走走」 | **不打断**（这正是用户抱怨的那个毛病） |

纯逻辑验收 17 例（`node tools/verify-bargein.mjs`）：7 个正例（含带标点、带空格、
句中包含）+ 8 个反例（咳嗽、旁人聊天、笑声、太小声的幻觉、空文本、无关指令）。

## 二十六、P3-d · 连续对话 + 托盘/播报修正（2026-10-28）

### 26.1 连续对话：由模型决定要不要接着听

原来每一轮都要先说「你好狼宝」。真实使用时是这样：问一句、它答一句、还得再叫一次，很蠢。

现在一轮说完，**如果模型认为话还没说完**，就不收窗口，直接开 9 秒待命窗口等你补充；
没等到人就自己收起。判断依据两条，取或：

1. 回复里出现 `[[继续]]` 标记（系统提示第 8 条要求模型在"等你回答"时输出）；
2. 回复最后一句是问句（模型忘了打标记时的兜底）。

为什么交给模型而不是固定时长：问"要哪一个"时必须等，而"打开浏览器"已经办完了再多听 9 秒就是骚扰。
这个判断只有模型有材料做。

托盘新增 **连续对话** 开关（默认开）。关掉就是单次对话：说完就结束，行为回到之前。

### 26.2 记账式修正：三个被用户抓到的毛病

**一、托盘「语音唤醒」勾选和真实状态两套。** `--listen` 启动时直接开了麦，
菜单项却是 `checked: false` 建出来的，之后再没人同步——于是"勾被取消但照样能唤醒"。
现在 `syncWakeTray()` 在 startListening / stopListening 里强制对齐，日志里能看到
`tray wake checkbox → true/false`。

**二、小窗消失但声音还在。** 两个缺口：
- 合成好的音频在"窗口已收起"之后才送到渲染层 → 出声但没画面。现在播放前检查 `win.isVisible()`。
- 收起时正在合成的那一句，合成完仍会播。现在加了"代次"（`speechGen`）：`stopSpeaking()` 把代次 +1，
  合成返回时对不上就直接丢弃。

**三、把"不要动窗口"那条提示词撤掉。** 用户要求改回去——模型该不该最小化窗口，不该由我硬性禁止。

### 26.3 一个自己挖的坑

系统提示是**模板字符串**，我在里面用反引号包了 `` `[[继续]]` ``，反引号提前结束了模板，
`[[继续]]` 变成代码 → 每一轮都抛 `继续 is not defined`，整轮失败。
修法：提示词里不要用反引号，改用方括号原文。**提示词也是代码**，加标记时要留意转义。

## 二十七、会话记忆与网络搜索（2026-10-28 · 问答+修复）

### 27.1 会话记忆：之前根本没有

用户问"会话缓存是怎么处理的"时，代码的真实状态是：**没有会话记忆**。
`Agent.run()` 每次都新建 `[system, user]`，一轮结束全部丢弃。
所以此前"每次都是新会话"成立，但代价是连续对话里接不上话——
"第二个呢""刚才那个"这类追问必然答不出来，因为模型根本看不到上一轮。

现在改成"**一次唤醒 = 一次会话**"：

| 时机 | 行为 |
|---|---|
| 唤醒 | `resetSession('wake')` 清空 |
| 关麦 | `resetSession('mic-off')` 清空 |
| 同一会话内的下一轮（连续对话/打断后续） | 带上之前几轮的 user/assistant |

裁剪规则（`trimHistory`）：最多 10 条、3000 字，且**必须以 user 开头**——
消息序列从 assistant 开始时，部分模型会认为"用户还没说话"，出现答非所问。
工具消息（截图 base64 之类）一律不进历史，只记一轮里动过哪些工具名。

实测：

```
turn start history=0 "现在几点了"
turn start history=2 "刚才你说了什么"
```

### 27.2 网络搜索：没有，现在靠"开浏览器"

代码里唯一的出网请求是 LLM 的 `/chat/completions`。工具白名单只有 12 个 CUA 动作，
里面没有搜索。所以"查一下今天的天气"实际路径是：模型打开浏览器 → 在地址栏打字 → 截图看结果。

能work，但慢（一轮 10~20 秒），而且受页面结构影响。要真做搜索有两条路：

1. **浏览器驱动（现状）**：零依赖、不需要 key，缺点是慢且脆。
2. **真搜索工具**：接一个 HTTP 搜索接口（SearXNG 自建 / Bing Web Search / DuckDuckGo HTML），
   返回标题+摘要+链接。快，但要多一个出网通道和（通常）一个 key。

这条还没做，等用户定。

## 二十八、联网搜索接入（Tavily）（2026-10-28）

### 28.1 为什么值得单独接

"打开浏览器→地址栏打字→截图看结果"查一次实时信息要 10~20 秒，页面一改还可能废。
Tavily 是给 AI 用的搜索接口：它自己抓正文并给一段 `answer`，
所以返回给模型的东西可以很短——语音助手不需要十条链接，需要一句能念的话。

### 28.2 实现要点

| 决定 | 理由 |
|---|---|
| 没配 key 时**工具不出现**在列表里 | 模型不会去调列表里没有的工具；比"调了再报错"干净 |
| `include_answer: true`、`search_depth: basic` | 语音场景要的是那句话；advanced 慢一倍还更贵 |
| 返回文本而非 JSON | 模型读"查询/要点/来源"这种文本更稳，长 JSON 容易把模型带进幻觉 |
| 摘要截断 320 字 | 太长会把上下文挤掉，且念不出来 |
| 同查询 5 分钟缓存 | 连续追问同一件事时不必重复打接口，也省钱 |
| 默认 `allow` + 审计留痕 | 查天气不该每次弹确认卡片；但查询词会外发，所以必须记一条 |

权限：新增能力 `web.search`（标准档 `allow`，`audit: true`）。用户可在设置里改成 `ask`。

### 28.3 配置

```bash
node tools/set-search-key.mjs tvly-xxxxxxxx   # 写进 .config/agent.json
node tools/set-search-key.mjs --clear         # 清除
# 或：set TAVILY_API_KEY=tvly-xxxx（环境变量优先，不落盘）
```

写入走 `store.saveConfig`（临时文件 + rename），和界面同一条路径；
读取给界面的值一律打码（`maskKey`），`null` 表示清除、空串表示不修改。


`verify-websearch.mjs` 用真实 HTTP 起一个假 Tavily，验的是：请求字段名、返回文本结构、
缓存命中、401/500 报错姿势、无 key 时的行为、工具 schema 形状。
**为什么不用真接口做单测**：别人的额度不该被我的 CI 消耗，而且真接口会因为网络抖动时灵时不灵。

### 29.5 定稿：换成 GPT-SoVITS（银狼）并删除旧 TTS（2026-10-28 晚）

在此之前"独立软件"只是开发态脚本：`node tools/run-shell.mjs`。这一步把它变成可安装的 exe。

### 31.1 分层

```
语音助手.exe
resources/
  app.asar            代码（apps/ + packages/）+ 生产依赖
  app.asar.unpacked/  原生模块（sherpa-onnx .node）
  models/             ASR + KWS 模型（198MB）          ← extraResources
  gsv_worker.py       TTS worker（Python 读不到 asar）  ← extraResources
  .runtime/           可选：venv + 音色包（5.2GB）      ← CUA_VA_BUNDLE_RUNTIME=1 才打
```

安装包默认 **267.7MB**（含模型、不含 .runtime）。装完能唤醒、能识别、能操作电脑、能联网搜索，
只是**没声音**——需要发声就把 `.runtime` 放到安装目录的 `resources/` 下。

### 31.2 路径必须重做

原来每个文件都写 `'models/...'` 相对路径，打包后全错。新增 `packages/config/paths.mjs`：

| 函数 | 打包后 | 开发态 |
|---|---|---|
| `modelPath()` | `resources/models/…` | `./models/…` |
| `runtimePath()` | `resources/.runtime/…` | `./.runtime/…` |
| `dataPath()` | `%APPDATA%/语音助手/data/…` | `./.config/…` |

**为什么是函数不是常量**：ESM 的 import 在主进程设置环境变量之前求值，常量会在那一刻钉死成 cwd。

用户数据（配置、审计、日志）全部搬出安装目录：安装目录通常不可写。

### 31.3 三个踩到的坑

1. **`Cannot create symbolic link`**：electron-builder 解压 winCodeSign 时要为 darwin 的 dylib 建符号链接，普通用户没权限，整个构建直接挂。关掉 `signAndEditExecutable` 绕过（代价：exe 无自定义图标）。
2. **`--listen` 变 "bad option"**：这台机器的环境里带着 `ELECTRON_RUN_AS_NODE=1`，打包后的 exe 会退化成 Node。启动测试脚本必须显式 `Remove-Item Env:ELECTRON_RUN_AS_NODE`。
3. **`app.setLoginItemSettings` 写错值名**：它把 Run 项写成了 `electron.app.Electron`，于是 `getLoginItemSettings()` 永远读回 false——用户看到"勾了但不生效"。改成自己写 `HKCU\...\Run\语音助手`，读回也用 `reg query`，状态一致。

## 三十二、R14 资源策略：全屏/内存紧张时让路（2026-10-28 晚）

### 32.1 为什么

TTS worker 常驻 **1.5GB 显存**、ASR 常驻 **240MB 内存**，打完游戏才发现它们一直在那儿。
用户的原需求是"不干扰工作/游戏"，所以要有主动让路，而不是等用户去托盘里手动关。

### 32.2 让路两档，都保留唤醒

| 触发 | 动作 | 代价 |
|---|---|---|
| 前台窗口盖住**整块显示器** | 关掉 TTS worker，释放 1.5GB 显存 | 游戏期间没声音（字幕照常，并提示"全屏中，语音已让出"） |
| 可用内存 < 1200MB | 卸载 ASR（240MB） | 唤醒仍有效（KWS 只有 3.3MB），唤醒后首次要多等 6 秒加载识别 |

**为什么保留 KWS**：唤醒是"这个软件还活着"的唯一证据。为省 3MB 把唤醒也关掉，
用户只会认为软件死了。

**正在对话/播报/等确认时一律不动**（`busy` 直接返回 `ok`）——那是最不能卡的几秒。

### 32.3 一个必须钉死的判定细节

判断"全屏"用的是**整块显示器**（rcMonitor）而不是工作区（rcWork）。
如果按工作区算，用户平常"浏览器最大化"就是 100%，语音会被一直关掉。
真正的全屏游戏会盖住任务栏、等于整块显示器；最大化窗口只到工作区，约 96%（实测 1707×1019 vs 1707×1044）。

单测里专门有一条 `全屏判定：最大化窗口 → false`，就是防止这个回归。

### 32.4 两个 PowerShell 坑（都踩了）

1. **here-string 终止符 `"@` 必须独占一行**。写成 `"@ -ErrorAction Stop` 会让 parser 崩，
   报错却指向 here-string 内部的 `using System;`（MissingUsingStatementDirective），完全误导。
2. **脚本文件必须 UTF-8 带 BOM**。PowerShell 5.1 会按 ANSI 读无 BOM 文件，中文注释被拆成乱码字节，
   能把 here-string 提前截断。症状同样是"报错行号跟内容对不上"。

## 三十三、收尾：P3 三项 + 密钥加密 + 日志轮转（2026-10-28 夜）

### 33.1 密钥加密（DPAPI）

文档从 P0 就写着"API Key 明文落盘，P3 接权限体系时一起加密"，一直没做。现在做了：

- 主进程启动时用 Electron `safeStorage`（Windows 下就是 DPAPI）注入加解密钩子
- `store` 写文件前加密成 `enc:<base64>`，读文件后解回明文
- **只对当前 Windows 用户可解**：配置文件被拷走也没用
- 没有钩子的场景（命令行工具、单测）照旧明文——所以 `tools/set-search-key.mjs` 依然可用
- 万一读到密文却没有钩子，`resolveApiKey()` **明确报错**，绝不把密文当密钥发出去（这条最容易写错）

托盘「导出审计日志…」与设置页「导出全部」按钮都接到 `exportAudit()`：

没有做"另存为"对话框——语音助手的场景是留档，不是挑路径。

### 33.3 允许 15 分钟（allow_once）

确认卡片从两个按钮变成三个：**允许 / 15 分钟 / 拒绝**。

- 点「15 分钟」→ `gate.grantOnce(capability, 15)`，15 分钟内同一能力的 `ask` 直接放行
- 授权只记能力，不记某次具体调用——这正是"别老弹卡片"的意思
- 引擎层早就支持 `allow_once`/`grantOnce`，缺的一直是这个入口

### 33.4 日志轮转

`assistant.log` / `shell.log` 超过 5MB 时改名为 `.1` 并重开。每写 200 行检查一次大小，
不用定时器——日志只会在写的时候长大。

## 三十九、缩短逐句间隔（2026-10-28 深夜）

### 39.1 间隔是哪来的

原来每一句都是"合成 → 播 → 播完再合成下一句"，所以句间空档 = **下一句的整段合成时间**
（实测 0.7~1.5 秒）。听感就是"说完一句先愣一下"。

再加两处隐形静音：GPT-SoVITS 每句首尾自带 100~300ms 静音，逐句播放时会累加。

### 39.2 两个改动

| 改动 | 做法 | 效果 |
|---|---|---|
| **预取（prefetch）** | 当前句还在播的时候，就把后面 2 句交给 worker 合成（`TTS_PREFETCH = 2`） | 句间空档从"一次合成"降到"一次 IPC" |
| **掐首尾静音** | worker 里 `trim_silence()`：相对峰值 1%（约 -40dB）以下算静音，保留 25ms 气口 | 每句短 0.2~0.4 秒 |

保留 25ms 气口是故意的：剪到 0 会把字头/字尾的爆破音削掉，听起来"咬字被砍了"。

### 39.3 实测

同一句"用三句话介绍一下北京"、切成 7 段播放：

```
13:48:15  spoken 1 ok synth=1635ms
13:48:17  spoken 2 ok synth=1187ms
13:48:20  spoken 3 ok synth=1392ms
...
```

日志里 **一条 `speech gap` 都没有**（这个日志只在间隔 >120ms 时打印）——
也就是句间断档已经低于 120ms。改之前每句之间是 700~1500ms。

prefetch 之所以够用：合成 1.1~1.6s，而一句的播放时长通常 1.5~3s，合成总能在播完前完成。

### 39.4 验收

```bash

```
## 四十、标点停顿：把切分权还给模型（2026-10-28 深夜）

### 40.1 上一版为什么没用

上一版只解决了"句与句之间的空档"（prefetch + 掐静音），但用户反馈 **标点处停顿依然大**。

真正的原因在切分，不在间隔：

1. 模型是**一句一句吐**的，我们每吐一句就立刻合成一句；
2. 每合成一句，对 TTS 模型来说都是**一次独立的完整朗读**——它会认真收尾、拖长尾音、留句末静音；
3. 于是我们切出来的每个句号都变成一次"句号级"停顿，比真人说话顿得多。

一句话：**停顿是我们切出来的，不是模型自然说的。**

### 40.2 两个改动

| 改动 | 做法 |
|---|---|
| **攒批** | 收到句子先不进合成，攒 220ms（或满 180 字）；期间又来新句子就继续合并 |
| **只切第一刀** | 合并后只把开头切到 18 字以内（保证尽快出声），剩下的整段（≤160 字）一次性合成 |

标点停顿从此由模型按语义自己给——逗号短、句号稍长，而不是每次都"喘一口气"。

代价：最后一句晚 0.2 秒出声；第二块整段合成要 2 秒左右，但这 2 秒正好被第一块的声音盖住。

### 40.3 实测（同一句"用三句话介绍一下北京"）

改前：**6 段**，每段 1.1~3.4 秒，6 次人工停顿
改后：**2 段**

```
13:53:55  spoken 1 ok dur=2673ms  「北京是中国的首都，也是全国的政治…」
13:54:09  spoken 2 ok dur=13570ms 「文化和国际交往中心。它有三千多年…」
```

第二段 13.6 秒一口气说完，中间所有标点停顿都是模型自己的节奏。
两段之间空档约 70ms（`speech gap` 日志没触发，阈值 120ms）。

### 40.4 可调参数

| 参数 | 位置 | 说明 |
|---|---|---|
| `CUA_VA_SPEECH_FLUSH_MS` | 环境变量 | 攒批窗口，默认 220ms |
| `SPEECH_FLUSH_CHARS` | main.mjs | 攒到 180 字立刻合成 |
| `FIRST_MAX` / `CHUNK_MAX` | `splitForSpeech` | 第一块 18 字 / 后续块 160 字 |
| `trim_silence(threshold, pad_ms)` | gsv_worker.py | 1.5% 峰值 / 12ms 气口 |

## 四十二、"说关了其实没关"与完整版打包（2026-10-28 深夜）

### 42.1 根因：三个错误叠在一起

用户让助手关掉某个程序，它回答"进程列表里已经没有它了"，但进程其实还在跑。

1. **`stop` 只是发了个 WM_CLOSE 就报成功**。有未保存内容的程序会弹确认框、托盘的只关窗口不退出，
   这些都不是"已结束"。
2. **校验用的是 `list`，而 `list` 只列"有窗口的进程"**。窗口一关它就看不见了，
   于是"看不见"被当成"退出了"——这是最要命的误判。
3. **没有区分"我请它关了"和"它真的没了"**，回话里给的确定性远超事实。

### 42.2 修法

`app_control` 重写：

| 动作 | 行为 |
|---|---|
| `list` | 保持原样（有窗口的），但文案里说明它**只**列有窗口的 |
| `find` | 新增：按名字查**全部**进程（含后台/托盘），带 pid 与路径 |
| `stop` | 发 WM_CLOSE 后**轮询等 3 秒**，还活着就明确回"没有真的退出，还剩 N 个进程（pid…）"，并问要不要强杀 |
| `stop force=true` | 强杀后再轮询 2 秒确认，确认没了才报成功 |

另外加了一条保护：**过滤掉自己的进程**。TTS worker 也是 `python.exe`、CUA 桥接也是 `powershell.exe`，
用户说"关掉 python"时不能顺手把助手的嗓子关了（实测发生过一次，一次 stop 端掉了 worker）。

### 43.2 但发现一个真 bug：退出被从中间掐断

## 四十八、唤醒状态重启丢失（2026-10-28 深夜）

### 48.1 为什么

"语音唤醒开着"这件事以前**只活在内存里**：

- 启动时只有带 `--listen` 参数才会开麦；
- 托盘里那个勾是运行时状态，退出就没了；
- 配置里根本没有 `ui.wakeEnabled` 这一项。

结果：双击启动 → 麦没开 → 用户以为"上次明明开着"。而且他如果不带 `--listen` 启动，
**必须每次手动去托盘勾一次**，这正是"状态没保存"的感受。

### 48.2 修法

1. 配置新增 `ui.wakeEnabled`（默认 **true**——这是个唤醒词助手，开箱不该是"麦没开"）。
2. 启动时按配置恢复：开了就 `startListening()`，关了就不开。
3. 托盘勾选（用户主动操作）会**落盘**。
4. `--listen` 不再硬开麦：如果你上次自己关了唤醒，带 `--listen` 启动也不会强开。
5. 程序内部调用（退出时 `stopListening`）**不落盘**——否则退出写进"关"，下次开机就不响了。

### 48.3 验收（两个方向都测了）

```
wakeEnabled=false → restore wake: off（上次是你自己关的）
                 → listen mode: 上次已关闭唤醒，本次不开麦（托盘里可再打开）

wakeEnabled=true  → restore wake: on
                 → listening started: {"ok":true,...}
```

### 48.4 一个容易踩的坑

`saveWakePreference` 必须和 `syncWakeTray` 分开：前者写文件，后者只改托盘勾。
把两者混在一起，退出流程里 `syncWakeTray(false)` 就会把"关"写进配置，
下次开机静悄悄——比"状态不保存"更难查。
## 四十九、连续对话交回模型判断：置信度映射时长（2026-10-28 深夜）

### 49.1 为什么不是 true/false

上一轮改回"永远等 9 秒"，是因为标记方案漏判；但固定等待又变成多等。
业界的做法都不是二选一，而是**把概率映射成等待时长**：

- LiveKit 用蒸馏的 Qwen2.5-0.5B 做 end-of-turn，输出概率
- Vapi 用 `waitFunction: "200 + 8000 * x"` 把概率换算成等待毫秒
- 拿不准就多等一会儿，判错也不致命

### 49.2 我们的实现

1. **判定单独发一次请求**（不混在长回复里）。只带最后一轮问答，要求输出
   `{"wait":bool,"confidence":0-1,"why":"…"}`。回复生成完就发起，和播报并行。
2. **置信度 → 窗口时长**：≥0.7 → 8 秒；0.3~0.7 → 4 秒；<0.3 → 1.5 秒（低于 low 且 wait=false 干脆不开）。
3. **判定慢也不怕**（实测 MiMo 2~6 秒，不稳定）：
   - 话说完先按启发式（问句/征询词/收尾语气）把窗口开起来，最多等判定 700ms；
   - 判定回来得晚：窗口还开着就按真实置信度**重调时长**；
   - 窗口已经关了、但判据说"有把握该等" → **补开**（只在话已说完、麦克风还在、用户没开始新一轮时）。

### 49.3 判定日志（调阈值的唯一依据）

```
follow-up judge: wait=true conf=0.85 src=test-fake 1ms
follow-up window 8000ms（conf=0.85）
follow-up outcome: silent after 8009ms (followup-timeout)
```

`outcome` 记录用户到底接话了没有——跑一周就能看出该把哪个阈值往哪边挪。

### 49.4 验收

```bash
node tools/verify-followup.mjs                      # 21 例：映射/启发式/JSON 解析/超时/报错
CUA_VA_JUDGE_FAKE="wait=1,conf=0.85,delay=3000" node tools/run-shell.mjs --followup-test
```

三个场景都验过：

| 判定 | 结果 |
|---|---|
| conf 0.9（晚到 3 秒，窗口已关） | 补开 8 秒窗口 ✓ |
| conf 0.1 | 不开窗口 ✓ |
| conf 0.85 | 一个窗口、8 秒、无重复 ✓ |

测试钩子 `CUA_VA_JUDGE_FAKE` 是必要的：真实模型延迟 2~6 秒且不稳定，
验收"晚到判定会不会重调"不能靠它碰运气。

### 50.1 症状

## 五十一、别一直确认 + 结构化字段别再念出来（2026-10-28 深夜）

### 51.1 提示词：把"确认"收成一次

原来规则 6 是"高风险动作执行前先向用户确认"，模型理解成了**每步都请示**，
一轮下来问三四次，每次都多烧一整个回合的 token。

改成：

> **只在真不可逆的时候问一次。** 删除、发送、支付、改系统设置这类做了就收不回的动作，
> 执行前问一次就够；用户已经说过"可以/好/就这样"之后，同一件事不要再问第二遍。
> 普通操作（打开、点击、输入、截图、搜索、查状态）**直接做，不要请示**。
> 做完也不要说"还需要我做别的吗"——用户会自己说。

同时把规则 7 换成"只输出说给用户听的自然语言"，明确点名 JSON、代码块、字段名、标记
（wait / confidence / why / [[继续]]）都是程序内部用的、念出来是噪音。

### 51.2 结构化字段漏进字幕和语音

用户听到并看到了 `{"wait":true,"confidence":0.9,"why":"…"}`——那是判定用的字段，
被主模型当正文吐出来了。

提示词约束是软的，所以加了一道**硬清洗**：`packages/agent/text.mjs` 的 `cleanLine()`：

| 清掉 | 例子 |
|---|---|
| 代码块 | ` ```json {…} ``` ` |
| 带内部字段名的 JSON | `{"wait":true,"confidence":0.9}` |
| 裸 key:value | `wait: true, confidence: 0.9` |
| 标记 | `[[继续]]` |
| 清完只剩标点的行 | `，{}，` → 整行丢掉（不能念出一串逗号） |

清完后还要收敛空悬的逗号/空格（`好的，{} 马上做` → `好的，马上做`），
但不能误伤书名号《三体》、英文路径 `C:\Users`。

### 51.3 为什么抽成独立模块

一开始 `cleanLine` 在 main.mjs 里，验收脚本只能"从源码里抠函数出来跑"——
那种测试一改格式就废（正则里的 `{` 直接把偷懒的切分逻辑搞崩了）。
现在它是 `packages/agent/text.mjs` 的纯函数，主进程只保留一行包装。

### 51.4 验收

```bash
node tools/verify-speechtext.mjs     # 14 例：清洗 + 不误伤
```

端到端实测（"帮我把记事本打开，然后随便写一句话"）：

```
我先打开记事本。 → launch_app
记事本起来了，我看看窗口。 → get_app_state
我换个方式找窗口。 → list_windows
编辑区找到了，我输入文字。 → set_value
记事本已经打开了，里面写了一句："今天也要记得多喝水，保持好心情。"
```

**5 次工具调用、0 次确认、0 个 JSON 泄漏**，17 秒跑完。
### 51.5 补充：不光是"确认"，还有"每步都复核"

用户补充的第二个问题：助手做完一步就调 `get_app_state` / `list_windows` 复核一次，
三步的活拖成七八步，每步都是一整轮 token。规则 2 原来是"先观察再动手"，
模型理解成了"动一下就看一眼"。

改成：

> **动作的结果已经写在工具返回里，不要每做一步就回头验证一遍。**
> 工具返回 ok、窗口列表、元素文本，就按它继续；只有返回信息真的不够
> （比如要点一个没见过的按钮）才去截图或读界面。
> **禁止"做完一个动作 → 再调一次 get_app_state/list_windows 确认"这种循环。**

实测同一句"打开记事本写一句话"：改动前 5 次工具调用（含 2 次重复 `list_windows`），
改动后 3 次（launch_app → get_app_state 找输入框 → type）。

### 51.6 待命窗口的观感：别跳"聆听中"

用户反馈"窗口不像自然关闭，关闭前出现了聆听状态"。

功能上没错（麦克风确实开着、直接说话就能接），但视觉上很怪：

## 五十二、放过歌的这一轮别再等（2026-10-30）

用户要求："执行放歌后，本轮取消连续对话"。

理由站得住：放歌是个明确的"去做事"动作，不是一个需要追问的对话。可原来的逻辑里，
回复一说完就按判定开一个待命窗口（4–8 秒），于是歌已经开始放了，界面还挂着"想继续说就直接说"，
麦克风继续等——歌里的人声还会一直往识别里灌，下一句很可能识别成歌词。

做法（只动判定，不动播放）：

- `handleAgentEvent` 收到 `tool_end` 且 `ok === true`，工具是 `music`（LX）或 `netease_music`（网易云），
  且这一轮的 action 属于 `play / resume / next / prev` → 置 `suppressFollowUp = true`
- `startFollowUpIfWanted` 一进来就被它挡住：不开窗口，`afterTurnSpeechSettled` 走常规收起（`done` + 1.5s 收窗）
- 判定回得晚、想"补开窗口"的那条分支也加了同一个条件，否则慢模型下会被它重新打开
- 每轮 `runCommand` 开头、以及每次 `onWake` 都清零——上一轮放过歌不影响这一轮

几个刻意的边界：

- **只有成功才算**：play 失败（LX 没连上、搜不到歌）时窗口照常开，用户还得接着说"那换成xx"
- **查询类不算**：`state` / `lyric` 这种只是问一句歌名，不该掐掉对话
- **换歌也算**：`next` / `prev` 同样是"让它去做事"

验收：`node tools/run-shell.mjs --music-followup-test`（不连模型、不开麦，直接喂工具事件）。
5 个用例全绿：play 成功→不开、play 失败→照开、state→照开、next 成功→不开、netease_music play 成功→不开。
